# Orchestrator Design v13 – spec13.txt (2026-07-15)
===========================================================
This revision adopts the native OpenAI‑compatible chat format for all LLM
calls.  `prompt_template` is removed from the model configuration; each
model now defines a `system_prompt` that is placed in the `"system"` role
of the messages array.  Tools are sent as a structured `tools` array,
and the full conversation history (including assistant tool‑calls and
tool results) is maintained across turns.  The job protocol for tool
calls carries the original tool‑call ID so that the parent job can
construct the proper reply sequence.

1. Overview
-----------
Yapo is a home‑lab orchestrator that manages stateless LLM jobs using a
folder‑based job pool.  A jobber serialises all state transitions.  The
main loop (`yapo.py`) picks jobs from `ready`, respects server and tool
capacity, and forks runner processes.  The runner assembles a structured
OpenAI‑compatible payload, calls the LLM via a pluggable backend
connector, and parses the standard chat‑completion response.  Context
accumulates as a conversation transcript; when it becomes too large, the
runner compacts it via MCP tool calls.

All tool execution (memory, summarisation, web search, shell commands,
and routing) is delegated to external MCP servers.  There are no separate
“embed”, “summarise”, or “router” job types – these are MCP tools.

LLM calls use `conn_openai.py`, which speaks the OpenAI‑compatible
`/v1/chat/completions` protocol.

2. Terminology
---------------
- Job type: `"main"` or `"tool"`.
- Model type: classification string used by the router or manual
  override.  Values include `"code"`, `"others"`, `"visual"`, etc.
- Model name: server‑side identifier passed to the LLM backend (e.g.
  `"qwen3-coder-30b"`).
- `system_prompt`: a string in `config.toml` under `[[models]]`; it becomes
  the `content` of the `"system"` role message.
- `conversation.json`: a persistent array of message objects that
  represents the entire dialogue with the LLM for a main job.
- `convergence_note`: dynamic instruction injected into the `"user"` role
  message, not the system prompt.

3. Folder Structure & States
-------------------------------
jobs/
  ready/
  processing/
  pending/
  done/
  error/

4. Job Folder Contents
-----------------------
  job.toml               – job metadata (job_id, type, model_type, parent,
                           tool_name, start_after, max_job_duration, etc.)
  parent.<qno>           – empty marker for parent queue number
  sub.<qno>              – empty marker per direct child
  prompt.txt             – the original user task
  conversation.json      – **NEW**: full conversation array (list of
                           message dicts) for the main job’s LLM history
  context.txt            – (legacy) accumulated tool results; may be
                           phased out in favour of conversation.json
  output.txt             – LLM response or tool result
  full_payload.json      – (diagnostic) exact JSON payload sent to LLM
  tool_call.json         – present in tool jobs; the entire tool‑call
                           object from the assistant message, including
                           the `id` (original call ID)
  assets/                – optional attached files

5. Component Summary
---------------------
5.1 jobber.py – unchanged except that creation of a main job now
    initialises an empty `conversation.json` array `[]`.

5.2 runner.py – major changes:
    - Builds payload using `system_prompt` from model config and the
      conversation history from `conversation.json`.
    - Tools are passed as a `tools` array of function definitions.
    - All model‑specific sampling parameters (`temperature`, `top_k`,
      `top_p`, `max_tokens`, `repeat_penalty`, etc.) from the model
      configuration are included in the request payload.
    - Convergence note appended to the current user message, not the
      system prompt.
    - When the LLM responds with `tool_calls`, the runner:
        1. Appends the user message to `conversation.json`.
        2. Appends the assistant message (including `tool_calls` with
           their original `id` values) to `conversation.json`.
        3. Creates one tool child job per tool call, storing the exact
           tool‑call object (with `id`) in the child’s `tool_call.json`.
        4. Moves the main job to `pending`, waiting for all children.
        5. When a tool child completes, its result is used to construct a
           `"tool"` role message (`role: "tool"`, `tool_call_id`, `name`,
           `content`), which is appended to `conversation.json`.
    - Once all children are done, the main job returns to `ready` and
      the next LLM call includes the full updated history.
    - Compaction still uses MCP tools but now captures the transcript from
      `conversation.json`.

5.3 yapo.py (scheduler) – unchanged.

5.4 init.py – unchanged.

5.5 dashboard.py – unchanged.

5.6 conn_openai.py – already sends JSON; the runner now supplies the
    `tools` array directly.  The connector must handle `tool_calls` in
    the response (standard OpenAI format) and return the full
    `choices[0].message` so that the runner can extract `content` and/or
    `tool_calls`.

6. Configuration Changes
--------------------------
- Removed: `prompt_template` from `[[models]]`.
- Added: `system_prompt` (string) – placed in the `"system"` message.
- Example model entry:
```toml
[[models]]
name = "qwen3-coder-30b"
type = "code-qwen3"
server = "gpu"
tool_allowed = true
temperature = 0.1
max_tokens = 8192
top_k = 20
top_p = 0.85
repeat_penalty = 1.05
system_prompt = "You are an expert coding assistant. Output only valid JSON: {\"done\":true,\"answer\":\"...\"} or a tool call."

    Prompt Construction (Main Jobs)

7.1 Conversation Initialisation
When a main job is first created, its conversation.json is [].

7.2 Building the Payload

    Start with messages array containing the system message:
    {"role": "system", "content": "<system_prompt>"}

    Append all messages from conversation.json (the history).

    Append a new user message composed of:

        The original task from prompt.txt (and any new instructions)

        The dynamic convergence note (injected at the end).
        Role: "user".

    If the model tool_allowed is true, build the tools array from
    all non‑route_prompt tools, each as a function definition
    following the OpenAI format:
    json

    {
      "type": "function",
      "function": {
        "name": "tool_name",
        "description": "...",
        "parameters": { "type": "object", "properties": {...}, "required": [...] }
      }
    }

    Set model, temperature, and any other sampling parameters
    (top_k, top_p, max_tokens, etc.) from the model config.

7.3 Dynamic Convergence Note
Same escalation as before, but placed inside the user message:

    Turn 1‑2: "If the task is a straightforward coding or writing request that you can complete with your own knowledge, do it immediately without calling any tool."

    Turn 3: "You have called tools several times. You MUST now provide the final answer using the information you have. Do NOT call any more tools."

    Turn ≥4: "This is your LAST chance. Produce the final answer NOW. Do NOT call any tools."

7.4 Conversation History Maintenance & Tool‑Result Loop
After each LLM call, the runner performs these steps in order:

    Append the user message that was just sent to conversation.json.

    Append the complete assistant message returned by the LLM to
    conversation.json. This message may contain:

        "content": "final answer" if the job is done, or

        "content": null and a "tool_calls" array with one or more
        tool‑call objects, each having an id, type, and function
        (containing name and arguments). This assistant message
        is kept exactly as returned by the LLM, preserving all
        original tool‑call IDs.

    If the assistant called tools:
    a. Create one tool child job per tool call. Each child’s
    tool_call.json receives the corresponding tool‑call object
    from the assistant message (including its id).
    b. Move the main job to pending and wait for all children.

    When a tool child finishes, its result is read from the child’s
    output.txt. The parent runner then appends a "tool" role
    message for that result, using the saved id from the child’s
    tool_call.json:
    json

    {
      "role": "tool",
      "tool_call_id": "<call_id>",
      "name": "<function_name>",
      "content": "<tool_result_json_string>"
    }

    If the assistant called multiple tools in one turn, there will be
    multiple "tool" messages, one per tool call, appended in the
    same order as the calls.

    Once all children have finished and their "tool" messages are
    appended, the main job returns to ready. The next LLM call will
    see the full history: user message → assistant message (with
    tool_calls) → tool result messages.

Example of conversation.json after one tool call round:
json

[
  {"role": "system", "content": "You are a helpful assistant."},
  {"role": "user",   "content": "Search for the weather in London."},
  {"role": "assistant", "content": null,
   "tool_calls": [
     {
       "id": "call_abc123",
       "type": "function",
       "function": {
         "name": "web_search",
         "arguments": "{\"query\":\"London weather\"}"
       }
     }
   ]
  },
  {"role": "tool",
   "tool_call_id": "call_abc123",
   "name": "web_search",
   "content": "{\"status\":\"success\",\"results\":[\"London: 18°C cloudy\"]}"
  }
]

7.5 Mandatory Compliance
The conversation history must always follow the OpenAI specification:

    A user message that triggered the assistant’s tool calls.

    The assistant message containing the original tool_calls (with
    id values).

    For each tool call, a tool message with matching tool_call_id.
    The runner must never omit or reorder these steps.

    Tool Job Execution

    The runner for a tool job reads tool_call.json (the full tool‑call
    object from the assistant message), extracts the function name and
    arguments, and calls the corresponding MCP tool.

    The MCP tool result is written to output.txt.

    The parent job’s runner, upon detecting all children done, appends the
    "tool" message(s) as described in 7.4.

    LLM Output Parsing

The runner expects a standard chat completion. The choices[0].message
may contain:

    content (string) – the final answer (implies done).

    tool_calls – an array of tool call objects.

If tool_calls is present, the runner creates one tool child job for
each call. Each child’s tool_call.json contains the corresponding
tool‑call object (including its unique id).

    Compaction

Triggered when conversation.json exceeds compact_size_kb. The
runner:

    Extracts the conversation text (all non‑tool messages).

    Calls summarise_text and mem_write/mem_read.

    Creates a clone job with a fresh conversation.json containing only
    the system message and a summary context message.

    GPU Energy Management – unchanged.

    REST API – unchanged.

    Open Issues – none.
