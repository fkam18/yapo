Orchestrator Design v10 – spec10.txt (2026-07-07)
==================================================
This revision documents the model_type semantics, per‑model prompt
templates with ChatML support, reasoning‑mode control, the route_prompt
tool exclusion from the LLM‑visible tool list, the dynamic convergence
notes, and the corrected default routing flow.

1. Overview
-----------
Yapo (Yet Another Personal Orchestrator) is a home‑lab orchestrator that
manages stateless LLM jobs using a folder‑based job pool.  A jobber
serialises all state transitions.  The main loop (`yapo.py`) picks jobs
from the `ready` state, respects server and tool capacity, and forks
runner processes.  The runner assembles a standardised prompt (using a
per‑model template when configured), calls the LLM via a pluggable
backend connector, and parses a structured JSON output.  Context
accumulates across turns; when a main job’s context becomes too large,
the runner compacts it via MCP tool calls before the next LLM call.

All tool execution (memory, summarisation, web search, shell commands,
and routing) is delegated to external MCP servers.  There are no separate
“embed”, “summarise”, or “router” job types – these are MCP tools called
directly.

LLM calls use `conn_openai.py`, which speaks the OpenAI‑compatible
/v1/chat/completions protocol (Ollama, llama.cpp, and cloud providers).

The system is designed for home use with a GPU server that is not always
powered on.  The scheduler enforces per‑server GPU power‑on windows,
on‑demand mode with idle timeout, Wake‑on‑LAN, and SSH suspend.  Jobs
can specify a start time and maximum duration.

All file operations are restricted to the configured `workspace` root.

2. Terminology
---------------
- **Job type** (`job.toml` field `"type"`): `"main"` or `"tool"`.
- **Model type** (`config.toml` model field `"type"`): the classification
  used by the router or manual override to select a concrete model.
  Values: `"code"`, `"others"`, `"visual"`, `"embed"`, `"summarise"`,
  `"router"`, and any user‑defined types (e.g. `"others1"`).
- **Model name** (`config.toml` model field `"name"`): the server‑side
  identifier passed to the LLM backend (e.g. `"others"`, `"coder"`).
  Multiple model types may share the same server‑side model name.

The CLI flag for forcing a model type is `--mtype`.  Available types are
read dynamically from `config.toml` by `init.py`.

3. Folder Structure & States
------------------------------
jobs/
  ready/         – jobs waiting to be picked by the scheduler
  processing/    – job currently being executed by a runner
  pending/       – job waiting for sub‑jobs (tool children) to finish
  done/          – job completed
  error/         – job failed (terminal)

All state changes are atomic via jobber (serialised by jobber.lock).

4. Job Folder Contents
-----------------------
  job.toml
    job_id            : 12‑char unique ID (same for entire task chain)
    type              : "main" or "tool"
    model_type        : model type string (e.g. "code", "others1").
                        Empty if not yet routed.  Set by init.py
                        (‑‑mtype) or by the runner via route_prompt.
    parent            : parent job queue number (0 if none)
    name              : human‑readable job name (optional)
    tool_name         : for tool jobs (informational)
    start_after       : HH:MM string; job waits until that time today
                        (or next day if already past).  (optional)
    max_job_duration  : integer seconds; overrides global default.
                        Default: 900 (15 min).  (optional)
    fail_on_child_error : bool (default false)
    compact           : if true, created by compaction
  parent.<qno>      – empty file indicating parent queue number
  sub.<qno>         – empty file per direct child (managed by jobber)
  prompt.txt        – the task for this job
  context.txt       – accumulated context (tool results, memory, etc.)
  output.txt        – LLM response (JSON) or tool result
  full_prompt.txt   – (diagnostic) exact prompt sent to LLM
  tool_call.json    – present only in tool jobs; JSON to forward to MCP
  assets/           – optional attached files

5. Component Summary
---------------------
5.1 jobber.py
    Serialised CRUD for jobs.  Key arguments:
      create  --type <type> --state <state>
              --model-type <model_type>   (v10: default empty → router)
              [--parent <qno>] [--prompt-file <file>]
              [--tool-json '<json>'] [--job-name <name>]
              [--start-after HH:MM] [--max-job-duration <seconds>]
      move    <qno> <new_state>
      append  <qno> <file> <text>
      clone   <qno> --new-jobid <id>
      cleanup <qno>

    `--model-type` defaults to an empty string.  When empty, the runner
    invokes the `route_prompt` MCP tool to classify the prompt.

5.2 runner.py
    Executes a job from the processing state.
    - If type == "tool":
        Execute the MCP tool, write result, propagate to parent.
    - If type == "main":
        * If `model_type` is empty → call `route_prompt` MCP tool,
          store the returned classification in job.toml.
        * If `model_type` is set → skip routing.
        * Look up the model config by `type` (not by name) to get the
          server model name, server URL, options, and prompt_template.
        * Build the prompt using the model's `prompt_template` if
          present, otherwise use the default XML template (backward
          compatible).  The `route_prompt` tool is excluded from the
          tool list sent to the LLM.
        * Inject the dynamic convergence note (based on turn number)
          into the template via the `{{convergence_note}}` placeholder.
        * Call the LLM, parse the JSON output, handle tool calls / done.
    **Tool‑call loop guard:** hard cap of 5 total tool calls.
    **Dynamic convergence:** three‑tier escalation injected at build time.

5.3 yapo.py (scheduler)
    (Unchanged from v9 – enforces start_after, max_job_duration,
     per‑server GPU schedule, capacity, WoL/suspend.)

5.4 init.py
    Entry point: creates a main job from a user prompt.
    Usage: init.py "prompt"
           [--mtype <model_type>]   (v10: dynamic choices from config)
           [--name "job name"]
           [--start-after HH:MM]
           [--max-duration <seconds>]
           [--rag <tool>:<query> ...]

    If `--mtype` is given, the model type string is stored directly in
    job.toml.  If omitted, `model_type` is left empty and the runner
    will route the prompt automatically.

5.5 Auxiliary tools
    - `catjob.py <qno>` – prints job details and output.
    - `catanswer.py` – extracts the `answer` field as plain text.
    - `dashboard.py` – web dashboard on port 3388 with job submission
      form, queue auto‑refresh, job detail panel, raw/answer toggle,
      copy button.  Displays both model_type and resolved model_name.

5.6 Backend Connection Module (conn_openai.py)
    (Unchanged from v9.  Includes optional DEBUG_DUMP flag for raw
     API response logging to /tmp/openai.txt.)

6. Prompt Templates
--------------------
6.1 Default XML Template
    Used when a model has no `prompt_template` in config.toml.
    Same structure as v8/v9: <GOAL>, <CONTEXT>, <TOOLS>, <RULES>, <TASK>.

6.2 Per‑Model Templates (v10)
    Models may specify a `prompt_template` string in config.toml.
    The runner performs variable substitution for:
      {{goal}}            – original user prompt
      {{context}}         – content of context.txt (or "(none)")
      {{tool_list}}       – generated tool list (route_prompt excluded)
      {{task}}            – current job prompt
      {{convergence_note}} – dynamic escalation text

    Templates may use ChatML tokens (<|im_start|>, <|im_end|>) for
    Qwen models or any other format required by the backend.

    Example (ChatML with reasoning limit):
    """
    <|im_start|>system
    You are an expert coding assistant. When asked to write code, output
    the complete code directly, not a plan or description.
    Think briefly (max 3 sentences), then provide your answer.
    Output ONLY valid JSON: {"done":true,"answer":"..."} or
    {"tool":"...","arguments":{...}}
    {{convergence_note}}
    <|im_end|>
    <|im_start|>user
    Goal: {{goal}}
    Context: {{context}}
    Tools: {{tool_list}}
    Task: {{task}}
    <|im_end|>
    <|im_start|>assistant
    """

7. LLM Output Parsing
----------------------
Valid outputs:
  - {"tool": "...", "arguments": {...}}
  - {"done": true, "answer": "..."}
Markdown fences are stripped before parsing.  A robust `extract_json()`
handles malformed responses by extracting the first valid JSON object.

11. Lifecycle Example (Revised)
-------------------------------
a) User runs: init.py "write a Rust program for a 9x9 Go game"
   (no --mtype).  jobber creates main job 1000 (model_type="").
b) Scheduler runs 1000.  Runner sees empty model_type, calls
   route_prompt → "code".  Stores model_type="code" in job.toml.
c) Runner looks up model type "code" → server model "coder",
   ChatML template with "output code directly" instruction.
   Builds prompt, calls LLM.
d) LLM returns {"done":true,"answer":"fn main() { ... }"}.
   Runner moves 1000→done.
