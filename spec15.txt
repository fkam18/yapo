# Orchestrator Design v15 – spec15.txt (2026-07-17)
===========================================================
This revision adds a persistent, sandboxed filesystem workspace for LLM
jobs.  A new `filesystem-mcp` server (simple stdio protocol) exposes
read/write/list/mkdir/search operations on a named Docker volume mounted
at `/ws`.  The dashboard (`dashboard.py`) gains REST endpoints for
manual upload/download/sync with the workspace.  All file tools return
**plain text** output for reliable LLM consumption, and the runner
detects errors via process exit codes – no JSON‑parsing required in the
conversation.

1. Overview
-----------
Yapo is a home‑lab orchestrator that manages stateless LLM jobs using a
folder‑based job pool.  A jobber serialises all state transitions.  The
main loop (`yapo.py`) picks jobs from `ready`, respects server and tool
capacity, and forks runner processes.  The runner assembles a structured
OpenAI‑compatible payload, calls the LLM via a pluggable backend
connector, and parses the standard chat‑completion response.  Context
accumulates as a conversation transcript; when it becomes too large, the
runner compacts it via MCP tool calls.

All tool execution (memory, summarisation, web search, shell commands,
**file operations**, and routing) is delegated to external MCP servers.
There are no separate “embed”, “summarise”, or “router” job types – these
are MCP tools.

LLM calls use `conn_openai.py`, which speaks the OpenAI‑compatible
`/v1/chat/completions` protocol.

2. Terminology
---------------
(Same as v14, with additions:)
- `workspace`: the persistent file storage rooted at `/ws` inside the
  `yapo` container, backed by a Docker named volume.  All file‑oriented
  MCP tools (and the dashboard REST API) operate strictly within this
  directory tree.

4. Job Folder Contents
-----------------------
(Unchanged from v14.)
  job.toml               – job metadata (job_id, type, model_type, parent,
                           tool_name, start_after, max_job_duration, etc.)
  parent.<qno>           – empty marker for parent queue number
  sub.<qno>              – empty marker per direct child
  prompt.txt             – the original user task
  conversation.json      – full conversation array (list of message dicts)
                           for the main job’s LLM history
  context.txt            – (legacy) accumulated tool results; may be
                           phased out in favour of conversation.json
  output.txt             – LLM response or tool result
  full_payload.json      – (diagnostic) exact JSON payload sent to LLM
  tool_call.json         – present in tool jobs; the entire tool‑call
                           object from the assistant message, including
                           the `id` (original call ID)
  assets/                – optional attached files

5. Component Summary
---------------------
5.1 jobber.py – unchanged except that creation of a main job now
    initialises an empty `conversation.json` array `[]`.

5.2 runner.py – major changes (v14 + v15):
    - (All v14 items remain)
    - **Plain‑text tool results**: MCP tools (including the new
      filesystem ones) write a human‑readable string to stdout.  The
      runner treats any non‑zero exit as a failure and moves the tool
      job to `error`.  A zero exit means success; the text becomes the
      `"content"` of the `tool` role message in the conversation.
    - The runner does **not** attempt to parse JSON from tool outputs;
      it uses them verbatim.  This keeps the LLM interface natural and
      avoids hallucination‑prone structured blobs.

5.3 yapo.py (scheduler) – unchanged.

5.4 init.py – unchanged.

5.5 dashboard.py – now shows tool‑call details and full job output.
    **New in v15**: exposes a set of REST endpoints for direct
    manipulation of the workspace volume (see §7.3).

5.6 conn_openai.py – unchanged from v14.

5.7 filesystem_mcp.py (new) – a simple stdio MCP server that handles
    `read_file`, `write_file`, `list_directory`, `create_directory`, and
    `search_files`.  All paths are confined to `/ws` using
    `os.path.realpath` and a prefix check.  Output is plain text (e.g.
    a directory listing with file sizes, or “File written successfully.”).

6. Configuration Changes (v14 + v15)
-------------------------------------
- (All v14 changes retained)
- Added `[[mcp_servers]]` entry for `filesystem-mcp` with `command =
  "python3"` and `args = ["/app/filesystem_mcp.py"]` (container path,
  transformed by the build‑time converter).
- Added `[[tools]]` entries for the five filesystem tools, all pointing
  to `mcp_server = "filesystem-mcp"`.

Example new configuration snippets:
```toml
[[mcp_servers]]
name = "filesystem-mcp"
transport = "stdio"
command = "python3"
args = ["/app/filesystem_mcp.py"]
protocol = "simple"
description = "Workspace file operations"

[[tools]]

description = "Read the contents of a file in the workspace"

implementation = "mcp"
mcp_server = "filesystem-mcp"
mcp_tool = "read_file"

# (similarly for write_file, list_directory, create_directory, search_files)

7. Filesystem Workspace (new in v15)

7.1 Docker Volume and Mount

    A named Docker volume workspace is declared in docker-compose.yml.

    The yapo service mounts this volume at /ws (read‑write).

    The filesystem_mcp.py script operates exclusively under /ws;
    path traversal is blocked by resolving to an absolute path and
    requiring that it starts with /ws/ or equals /ws.

7.2 MCP Filesystem Server

    filesystem_mcp.py implements the “simple” protocol (single JSON
    request, plain‑text response).

    Tools:

        read_file(path) → file content as text

        write_file(path, content) → confirmation message

        list_directory(path?) → human‑readable list with 📁/📄 icons

        create_directory(path) → confirmation

        search_files(path?, pattern) → grep‑like results

    The script returns a non‑zero exit code only for fatal errors
    (e.g. missing file). Logical errors (file not found within a
    successful script run) are returned as an error text string with
    exit code zero so the LLM can react gracefully.

7.3 Dashboard REST API for Workspace

    The dashboard (dashboard.py) now serves the following endpoints:

        GET /api/ws/list?path=<rel> – list directory contents

        GET /api/ws/download?path=<rel> – download a file

        POST /api/ws/upload – upload a file (JSON body with base64
        content)

        POST /api/ws/mkdir – create a directory

        DELETE /api/ws/delete?path=<rel> – delete file or empty dir

    All paths are relative to /ws and validated with the same
    confinement logic as the MCP server (_safe_ws_path method).

    These endpoints allow manual file sync between the developer’s
    laptop and the LLM’s workspace, without requiring the MCP
    protocol.

7.4 Plain‑Text Output Rationale

    Tool results are plain text rather than JSON to reduce LLM
    hallucination and to match the existing web_search and
    run_command tools.

    The runner relies on the MCP process exit code for binary
    success/failure; the LLM interprets any text the tool writes to
    stdout.

7.5 Build and Deployment

    The filesystem_mcp.py script resides in the repository root,
    alongside other MCP scripts. The Docker build context (COPY . .)
    includes it automatically.

    The convert-config.py script (used during image build) must
    translate the source path (/home/fkam/apps/yapo/filesystem_mcp.py)
    to the container path /app/filesystem_mcp.py, just as it does
    for the other MCP scripts.

    No changes to the Ansible playbook are required – the new script
    is embedded in the Docker image.

    Security Considerations

    Path confinement: Both filesystem_mcp.py and the dashboard API
    enforce that all file operations stay within /ws. Attempts to
    escape (e.g. ../../../etc/passwd) are rejected with HTTP 403 or a
    Python exception.

    Minimal privilege: The MCP server is a simple Python subprocess
    inside the yapo container; it inherits the container’s filesystem
    permissions. The workspace volume is separate from the system and
    application code.

    No network exposure: The filesystem tools are accessed only via
    MCP (local stdio); the REST API is the only external entry point and
    is intended for trusted LAN access (dashboard on port 3388).
