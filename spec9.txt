Orchestrator Design v9 – spec9.txt (2026-07-06)
================================================
This revision merges the GPU energy management clarifications,
implements per‑server GPU schedules, adds job time constraints
(start_after / max_job_duration), updates all component interfaces,
and documents the web dashboard submission form.

1. Overview
-----------
Yapo (Yet Another Personal Orchestrator) is a home‑lab orchestrator that
manages stateless LLM jobs using a folder‑based job pool.  A jobber
serialises all state transitions.  The main loop (`yapo.py`) picks jobs
from the `ready` state, respects server and tool capacity, and forks
runner processes.  The runner assembles a standardised prompt, calls the
LLM via a pluggable backend connector, and parses a structured JSON
output.  Context accumulates across turns; when a main job’s context
becomes too large, the runner compacts it via MCP tool calls before the
next LLM call.

All tool execution (memory, summarisation, web search, shell commands,
and routing) is delegated to external MCP servers.  There are no separate
“embed”, “summarise”, or “router” job types – these are MCP tools called
directly.

LLM calls are made through a connection‑module abstraction.  The current
implementation uses `conn_openai.py`, which speaks the OpenAI‑compatible
/v1/chat/completions protocol.  This works with Ollama, llama.cpp,
DeepSeek, Together, Groq, and most cloud LLM providers.

The system is designed for home use with a GPU server that is not always
powered on.  The scheduler enforces per‑server GPU power‑on windows,
supports an on‑demand mode with idle timeout, and can trigger Wake‑on‑LAN
and passwordless SSH suspend.  Jobs can specify a start time and a
maximum duration to constrain execution to specific time windows and
prevent runaway jobs.

All file operations performed by tools are restricted to a configured
`workspace` root directory.

2. Terminology
---------------
- **Job type** (`job.toml` field `"type"`): the kind of work a job does.
  Possible values:
    `"main"`  – routes the prompt (if needed) and calls a main LLM.
    `"tool"`  – executes a single MCP tool and returns its result.
- **Model type** (`config.toml` model field `"type"`): the classification
  used by the router or manual override to select a concrete model.
  Possible values:
    `"code"`, `"others"`, `"visual"`, `"embed"`, `"summarise"`, `"router"`.

The CLI flag for forcing a model type is `--mtype` (used by `init.py`).

3. Folder Structure & States
------------------------------
jobs/
  ready/         – jobs waiting to be picked by the scheduler
  processing/    – job currently being executed by a runner
  pending/       – job waiting for sub‑jobs (tool children) to finish
  done/          – job completed
  error/         – job failed (terminal)

All state changes are atomic via jobber (serialised by jobber.lock).

4. Job Folder Contents
-----------------------
  job.toml
    job_id            : 12‑char unique ID (same for entire task chain)
    type              : "main" or "tool"
    model             : model name (empty if not yet routed, or for tool jobs)
    parent            : parent job queue number (0 if none)
    name              : human‑readable job name (optional, displayed in dashboard)
    tool_name         : for tool jobs (informational)
    start_after       : HH:MM string; job will not start before this time today.
                        If the current time is already past, the job waits until
                        the same time the next day.  No date concept – times are
                        relative to the Yapo startup day.  (optional)
    max_job_duration  : integer seconds; if the job runs longer than this, the
                        scheduler moves it to error with a timeout reason.
                        Overrides the global `max_job_duration` config value.
                        Default: 900 (15 minutes).  (optional)
    fail_on_child_error : bool (default false) – if true, parent moves to
                          error when any child fails
    compact           : if true, indicates this job was created by compaction
  parent.<qno>      – empty file indicating parent queue number
  sub.<qno>         – empty file per direct child (managed by jobber)
  prompt.txt        – the task for this job
  context.txt       – accumulated context (tool results, memory, etc.)
  output.txt        – LLM response (JSON) or tool result
  full_prompt.txt   – (diagnostic) exact prompt sent to LLM (written by runner)
  tool_call.json    – present only in tool jobs; contains the exact JSON
                      to forward to the MCP server
  assets/           – optional attached files

5. Component Summary
---------------------
5.1 jobber.py
    Serialised CRUD for jobs. Commands:
      create  --type <type> --state <state> [--model <model>] [--parent <qno>]
              [--prompt-file <file>] [--tool-json '<json>']
              [--job-name <name>] [--start-after HH:MM]
              [--max-job-duration <seconds>]
      move    <qno> <new_state>
      append  <qno> <file> <text>
      clone   <qno> --new-jobid <id>
      cleanup <qno>  (checks children, updates state)

    New arguments (v9):
      --job-name          : human‑readable name stored in job.toml
      --start-after       : HH:MM string (e.g. "22:00") – job waits until
                            that time today (or the next day if already past)
      --max-job-duration  : integer seconds; if the job runs longer than this,
                            the scheduler moves it to error.  Overrides the
                            global `max_job_duration` from config.toml.

    The old `finish_by` field has been removed and replaced by
    `max_job_duration`.

5.2 runner.py
    Executes a job from the processing state.
    - If type == "tool":
        Read tool_call.json, send it to the appropriate MCP server,
        write response to output.txt.  If the tool job has a parent,
        the runner propagates the result to the parent’s context.txt
        (prefixed with a marker `[TOOL:<tool_name>]`), removes the
        sub‑job reference, and moves the parent back to ready if all
        its children are done.
    - If type == "main":
        If the job has no model assigned (empty), call the `route_prompt`
        MCP tool to classify the original user prompt.  Set the job’s model
        to the returned model type (code, others, visual) and proceed.
        Before calling the LLM:
          * If there are no sub‑jobs and context.txt size exceeds
            compact_size_kb, perform context compaction (see §10).
            This may result in the job being moved to done and a clone
            created; runner returns without calling the LLM.
          * Otherwise, assemble the final prompt (see §6), call the LLM
            via the backend connector (§5.6), parse the output.
        After LLM output:
          - If output contains a tool call (JSON with "tool"), create a
            tool child job via jobber, providing the extracted JSON as
            --tool-json. Add sub.<child> file, move current job to pending.
          - If output contains "done", the job is complete. Move to done.
          - If the output is invalid, move to error.
    At the end, runner calls jobber cleanup on the parent if any.

    **Tool‑call loop guard:** To prevent infinite loops, the runner counts
    the total number of tool invocations for a given main job (by scanning
    `[TOOL:<tool_name>]` markers in context.txt).  A hard cap of 5 total
    tool calls forces completion.

    **Dynamic convergence:** The runner counts tool calls already made
    (the turn number) and passes it to `build_prompt()`.  The prompt
    template includes an escalating instruction that becomes increasingly
    insistent for the model to produce a final answer.

5.3 yapo.py (scheduler)
    Forever loop:
      - Scan ready/ for jobs, ordered by queue number.
      - For each, check:
          * `start_after`: if the job has a start time and the current time
            is before that time today, skip the job.  Jobs without a start
            time are immediately eligible.
          * `max_job_duration`: during the processing‑loop check, if a job
            has been in `processing` longer than its max duration (or the
            global default), move it to `error` with a timeout reason.
          * Server capacity (server reachable and slots available, if needed).
            Only servers with schedulable=true are considered.
            Server reachability is checked via the backend connector's
            `server_reachable()` function, falling back to a TCP ping.
          * Tool capacity (if job is a tool type).
          * GPU schedule windows (per‑server, see §12).
      - If eligible, move job ready→processing via jobber, fork runner.
      - Track runner PIDs; on exit, update capacity counters.
      - When a GPU schedule window ends or on‑demand idle timeout triggers,
        stop launching GPU jobs, wait for all active GPU jobs to finish,
        then suspend the GPU server (if Yapo woke it or if schedule demands).
      - If a GPU window is about to start or on‑demand requires a wake,
        send Wake‑on‑LAN to the server's mac_address.

5.4 init.py
    Entry point: creates a main job (type="main") from a user prompt.
    Usage: init.py "prompt"
           [--mtype code|others|visual]
           [--name "job name"]
           [--start-after HH:MM]
           [--max-duration <seconds>]
           [--rag <tool>:<query> ...]

    New arguments (v9):
      --start-after  : HH:MM string; passed to jobber as --start-after
      --max-duration : integer seconds; passed to jobber as --max-job-duration

    If `--mtype` is given, the corresponding model name is resolved from
    config.toml and placed directly in job.toml, skipping the router.
    The `--rag` flag creates tool children for pre‑fetching context before
    the main job runs.

5.5 Auxiliary tools
    - `catjob.py <qno>` – prints job details and output for the given
      queue number (automatically shows output.txt regardless of state).
    - `catanswer.py` – extracts the `answer` field from a job's JSON output
      and prints it as plain text.
    - `dashboard.py` – serves a web dashboard on http://0.0.0.0:3388
      showing all queues and job details (auto‑refreshing every 2 seconds).
      Includes a modal job submission form with fields for prompt, model
      type, job name, start‑after time, max duration, and RAG pre‑fetch.

5.6 Backend Connection Module (conn_openai.py)
    Yapo uses a pluggable backend abstraction for LLM calls.  Each backend
    is a module named `conn_<backend>.py` that implements two functions:

        generate(server_config, model, prompt, options) → str
            Send a prompt to the backend and return the raw response text.

        server_reachable(server_config, debug=False) → bool
            Return True if the backend server is accepting requests.
            When debug=True, diagnostic messages are printed to stderr.
            Falls back to a TCP connect if the HTTP health check fails.

    The current implementation is `conn_openai.py`, which uses the
    OpenAI‑compatible /v1/chat/completions endpoint.

6. Standard LLM Prompt Template (JSON output)
----------------------------------------------
<GOAL>
{original_user_prompt}
</GOAL>

<CONTEXT>
{context_text}
</CONTEXT>

<TOOLS>
{tool_list}
</TOOLS>

<RULES>
Your ENTIRE response must be EXACTLY ONE of the following JSON objects.
Do NOT add any text, markdown fences, or comments.

- If you need information, use a tool:  
  {
    "tool": "tool_name",
    "arguments": { "param1": "value1" }
  }

- Once you have the information (or if you already have enough), you MUST
  provide the final answer:  
  {
    "done": true,
    "answer": "Your final answer (any text, code, or Markdown)."
  }

IMPORTANT: If the context already contains search results, do NOT call the
same tool again. Use those results to answer immediately.
Never output both formats. The "answer" field may contain multiple lines.
</RULES>

<TASK>
{job_prompt}
</TASK>

7. LLM Output Parsing
----------------------
Valid outputs:
  - {"tool": "...", "arguments": {...}}
  - {"done": true, "answer": "..."}
The runner also strips leading/trailing markdown fences (``` ... ```)
before parsing.  A robust `extract_json()` function handles malformed
responses by extracting the first valid JSON object.  Any other output
moves the job to error immediately.

11. Lifecycle Example (Revised)
-------------------------------
a) User runs: init.py "search the web for iran usa war today" --mtype others
   jobber creates main job 1000 (type=main, model="gemma4:latest").
b) Scheduler runs 1000. Runner builds prompt with tools, calls LLM via
   conn_openai.
   LLM returns {"tool":"web_search","arguments":{"query":"iran usa war"}}.
   Runner creates tool child 1001, adds sub.1001, moves 1000→pending.
c) Scheduler runs 1001. Runner reads tool_call.json, calls the SearXNG
   wrapper, writes search results to 1001/output.txt. Runner propagates
   the result to 1000’s context.txt (prefixed with [TOOL:web_search]),
   removes sub.1001, moves 1000→ready.
d) Scheduler runs 1000 again. LLM now sees search results in context,
   returns {"done":true,"answer":"Here is a summary of the latest news…"}.
   Runner moves 1000→done.

12. GPU Energy Management (Revised v9)
---------------------------------------
12.1 Configuration (config.toml)
    Each GPU server carries its own schedule inside the server block.
    A global `max_job_duration` sets the default time limit for all jobs.

    Example:
    [[servers]]
    name = "gpu"
    url = "http://192.168.0.158:8080"
    schedulable = true
    max_jobs = 1
    mac_address = "34:97:f6:31:88:ee"
    suspend_command = "ssh -i ~/secrets/gpu/id_rsa -o BatchMode=yes oper@192.168.0.158 sudo systemctl suspend"

      [servers.gpu_schedule]
      timezone = "Europe/London"
      on_demand = true
      idle_timeout_seconds = 60
      windows = [
        { start = "22:00", end = "06:00" },
        { start = "12:00", end = "15:00" }
      ]

    Global default:
    max_job_duration = 900   # 15 minutes

    The schedule is per‑server, not global.  Multiple windows per day
    are supported (e.g., overnight and a daytime slot).  Windows are
    recurrent every day.  There is no date concept – times are 24‑hour
    HH:MM format.

12.2 Job Time Constraints
    Optional job.toml fields:
      start_after       : HH:MM string; job waits until that time today
                          (or the next day if already past).
      max_job_duration  : integer seconds; overrides the global default.
                          If the job runs longer, the scheduler moves it
                          to error with a timeout reason.

12.3 Scheduler Behaviour
    - `start_after`: during the ready‑queue scan, jobs with a start time
      before the current time are skipped.  Jobs without a start time
      are eligible immediately.
    - `max_job_duration`: during the processing‑loop, the scheduler
      checks each processing job's folder creation time.  If elapsed time
      exceeds the job's max duration (or the global default), the job
      is moved to `error`.
    - GPU reachability / WoL / suspend logic is unchanged from spec8
      except that the schedule is read from `server.gpu_schedule` instead
      of a global `gpu_schedule` section.
    - The `is_within_schedule` function uses local time (not UTC) and
      handles overnight windows.
