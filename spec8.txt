Orchestrator Design v8 – spec8.txt (2026-07-03)
================================================
This revision merges the OpenAI‑compatible backend addendum and updates
all "vl" references to "visual".

1. Overview
-----------
Yapo (Yet Another Personal Orchestrator) is a home‑lab orchestrator that
manages stateless LLM jobs using a folder‑based job pool.  A jobber
serialises all state transitions.  The main loop (`yapo.py`) picks jobs
from the `ready` state, respects server and tool capacity, and forks
runner processes.  The runner assembles a standardised prompt, calls the
LLM via a pluggable backend connector, and parses a structured JSON
output.  Context accumulates across turns; when a main job’s context
becomes too large, the runner compacts it via MCP tool calls before the
next LLM call.

All tool execution (memory, summarisation, web search, shell commands,
and routing) is delegated to external MCP servers.  There are no separate
“embed”, “summarise”, or “router” job types – these are MCP tools called
directly.

LLM calls are made through a connection‑module abstraction.  The current
implementation uses `conn_openai.py`, which speaks the OpenAI‑compatible
/v1/chat/completions protocol.  This works with Ollama, llama.cpp,
DeepSeek, Together, Groq, and most cloud LLM providers.

The system is designed for home use with a GPU server that is not always
powered on.  The scheduler enforces GPU power‑on windows, supports an
on‑demand mode with idle timeout, and can trigger Wake‑on‑LAN and
passwordless SSH suspend.

All file operations performed by tools are restricted to a configured
`workspace` root directory.

2. Terminology
---------------
- **Job type** (`job.toml` field `"type"`): the kind of work a job does.
  Possible values:
    `"main"`  – routes the prompt (if needed) and calls a main LLM.
    `"tool"`  – executes a single MCP tool and returns its result.
- **Model type** (`config.toml` model field `"type"`): the classification
  used by the router or manual override to select a concrete model.
  Possible values:
    `"code"`, `"others"`, `"visual"`, `"embed"`, `"summarise"`, `"router"`.

The CLI flag for forcing a model type is `--mtype` (used by `init.py`).

3. Folder Structure & States
------------------------------
jobs/
  ready/         – jobs waiting to be picked by the scheduler
  processing/    – job currently being executed by a runner
  pending/       – job waiting for sub‑jobs (tool children) to finish
  done/          – job completed
  error/         – job failed (terminal)

All state changes are atomic via jobber (serialised by jobber.lock).

4. Job Folder Contents
-----------------------
  job.toml
    job_id          : 12‑char unique ID (same for entire task chain)
    type            : "main" or "tool"
    model           : model name (empty if not yet routed, or for tool jobs)
    parent          : parent job queue number (0 if none)
    tool_name       : for tool jobs (informational)
    start_after     : ISO timestamp; job will not start before this (optional)
    finish_by       : ISO timestamp; job will be terminated if still running
                      after this (moved to error) (optional)
    fail_on_child_error : bool (default false) – if true, parent moves to
                          error when any child fails
    compact         : if true, indicates this job was created by compaction
  parent.<qno>      – empty file indicating parent queue number
  sub.<qno>         – empty file per direct child (managed by jobber)
  prompt.txt        – the task for this job
  context.txt       – accumulated context (tool results, memory, etc.)
  output.txt        – LLM response (JSON) or tool result
  full_prompt.txt   – (diagnostic) exact prompt sent to LLM (written by runner)
  tool_call.json    – present only in tool jobs; contains the exact JSON
                      to forward to the MCP server
  assets/           – optional attached files

5. Component Summary
---------------------
5.1 jobber.py
    Serialised CRUD for jobs. Commands:
      create  --type <type> --state <state> [--model <model>] [--parent <qno>]
              [--prompt-file <file>] [--tool-json '<json>']
      move    <qno> <new_state>
      append  <qno> <file> <text>
      clone   <qno> --new-jobid <id>
      cleanup <qno>  (checks children, updates state)
    When creating a tool job, --tool-json provides the exact JSON that will
    be placed in tool_call.json.

5.2 runner.py
    Executes a job from the processing state.
    - If type == "tool":
        Read tool_call.json, send it to the appropriate MCP server,
        write response to output.txt.  If the tool job has a parent,
        the runner propagates the result to the parent’s context.txt
        (prefixed with a marker `[TOOL:<tool_name>]`), removes the
        sub‑job reference, and moves the parent back to ready if all
        its children are done.
    - If type == "main":
        If the job has no model assigned (empty), call the `route_prompt`
        MCP tool to classify the original user prompt.  Set the job’s model
        to the returned model type (code, others, visual) and proceed.
        Before calling the LLM:
          * If there are no sub‑jobs and context.txt size exceeds
            compact_size_kb, perform context compaction (see §10).
            This may result in the job being moved to done and a clone
            created; runner returns without calling the LLM.
          * Otherwise, assemble the final prompt (see §6), call the LLM
            via the backend connector (§5.6), parse the output.
        After LLM output:
          - If output contains a tool call (JSON with "tool"), create a
            tool child job via jobber, providing the extracted JSON as
            --tool-json. Add sub.<child> file, move current job to pending.
          - If output contains "done", the job is complete. Move to done.
          - If the output is invalid, move to error.
    At the end, runner calls jobber cleanup on the parent if any.

    **Tool‑call loop guard:** To prevent infinite loops, the runner counts
    the total number of tool invocations for a given main job (by scanning
    `[TOOL:<tool_name>]` markers in context.txt).  If the same tool has
    been called 2 or more times, the runner ignores the tool request and
    forces a final answer, moving the job to done.  A hard cap of 5 total
    tool calls also forces completion.

    **Dynamic convergence:** The runner counts tool calls already made
    (the turn number) and passes it to `build_prompt()`.  The prompt
    template includes an escalating instruction that becomes increasingly
    insistent for the model to produce a final answer.

5.3 yapo.py (scheduler)
    Forever loop:
      - Scan ready/ for jobs, ordered by queue number.
      - For each, check:
          * Server capacity (server reachable and slots available, if needed).
            Only servers with schedulable=true are considered.
            Server reachability is checked via the backend connector's
            `server_reachable()` function, falling back to a TCP ping.
          * Tool capacity (if job is a tool type).
          * GPU schedule windows and job time constraints (start_after,
            finish_by).
      - If eligible, move job ready→processing via jobber, fork runner.
      - Track runner PIDs; on exit, update capacity counters.
      - When a GPU schedule window ends or on‑demand idle timeout triggers,
        stop launching GPU jobs, wait for all active GPU jobs to finish,
        then suspend the GPU server (if Yapo woke it or if schedule demands).
      - If a GPU window is about to start or on‑demand requires a wake,
        send Wake‑on‑LAN to the server's mac_address.

5.4 init.py
    Entry point: creates a main job (type="main") from a user prompt.
    Usage: init.py "prompt" [--mtype code|others|visual] [--rag <tool>:<query> ...]

    If `--mtype` is given, the corresponding model name is resolved from
    config.toml and placed directly in job.toml, skipping the router.
    The `--rag` flag creates tool children for pre‑fetching context before
    the main job runs.

5.5 Auxiliary tools
    - `catjob.py <qno>` – prints job details and output for the given
      queue number (automatically shows output.txt regardless of state).
    - `catanswer.py` – extracts the `answer` field from a job's JSON output
      and prints it as plain text.
    - `dashboard.py` – serves a web dashboard on http://localhost:3388
      showing all queues and job details (auto‑refreshing every second).

5.6 Backend Connection Module (conn_openai.py)
    Yapo uses a pluggable backend abstraction for LLM calls.  Each backend
    is a module named `conn_<backend>.py` that implements two functions:

        generate(server_config, model, prompt, options) → str
            Send a prompt to the backend and return the raw response text.

        server_reachable(server_config) → bool
            Return True if the backend server is accepting requests.

    The current implementation is `conn_openai.py`, which uses the
    OpenAI‑compatible /v1/chat/completions endpoint.  This works with
    Ollama, llama.cpp, and most cloud LLM providers.

    Servers in config.toml specify which backend to use via the `backend`
    field (defaults to `"openai"`).  An optional `api_key` field is
    supported for cloud providers.

    The runner imports the backend module and calls `generate()` for LLM
    requests.  The scheduler calls `server_reachable()` for health checks.

    Health checks default to `/v1/models`.  If the backend module does not
    provide `server_reachable`, the scheduler falls back to a simple TCP
    connect on the server's host:port.

6. Standard LLM Prompt Template (JSON output)
----------------------------------------------
<GOAL>
{original_user_prompt}
</GOAL>

<CONTEXT>
{context_text}
</CONTEXT>

<TOOLS>
{tool_list}
</TOOLS>

<RULES>
Your ENTIRE response must be EXACTLY ONE of the following JSON objects.
Do NOT add any text, markdown fences, or comments.

- If you need information, use a tool:  
  {
    "tool": "tool_name",
    "arguments": { "param1": "value1" }
  }

- Once you have the information (or if you already have enough), you MUST
  provide the final answer:  
  {
    "done": true,
    "answer": "Your final answer (any text, code, or Markdown)."
  }

IMPORTANT: If the context already contains search results, do NOT call the
same tool again. Use those results to answer immediately.
Never output both formats. The "answer" field may contain multiple lines.
</RULES>

<TASK>
{job_prompt}
</TASK>

7. LLM Output Parsing
----------------------
Valid outputs:
  - {"tool": "...", "arguments": {...}}
  - {"done": true, "answer": "..."}
The runner also strips leading/trailing markdown fences (``` ... ```)
before parsing.  A robust `extract_json()` function handles malformed
responses by extracting the first valid JSON object.  Any other output
moves the job to error immediately.

8. Tool System & MCP Integration
---------------------------------
All tools are backed by MCP servers.  The tool registry is built by
querying each MCP server's tools/list endpoint at startup (cached in
`jobs/.tool_cache.json`).

8.1 MCP Servers (config.toml)
    Each MCP server is defined with transport, command/args, optional
    environment variables, and a protocol field.

    Example:
    [[mcp_servers]]
    name = "yapo-mcp"
    transport = "stdio"
    command = "python3"
    args = ["/home/fkam/apps/yapo/yapo_mcp.py"]
    protocol = "simple"
    description = "Router, memory and summarisation"

    [[mcp_servers]]
    name = "searxng-mcp"
    transport = "stdio"
    command = "python3"
    args = ["/home/fkam/apps/yapo/web_search_mcp.py"]
    protocol = "simple"
    env = { SEARXNG_URL = "http://app2.alt:8080" }
    description = "Web search via SearXNG (custom wrapper)"

    [[mcp_servers]]
    name = "shell-mcp"
    transport = "stdio"
    command = "python3"
    args = ["/home/fkam/apps/yapo/shell_mcp.py"]
    protocol = "simple"
    env = { YAPO_WORKSPACE = "/home/fkam/apps" }
    description = "Restricted shell command execution"

    The `protocol` field can be:
      - "simple"  – custom JSON format: {"tool":..., "arguments":...}
      - "jsonrpc" – standard JSON‑RPC (used for off‑the‑shelf MCP servers)

8.2 Tool Definitions (config.toml)
    Tools carry a `timeout_seconds` and reference an MCP server.

    [[tools]]
    name = "route_prompt"
    description = "Classify a prompt as code, others, or visual"
    parameters = [{ name = "prompt", type = "string", required = true }]
    concurrent_calls = 10
    timeout_seconds = 30
    implementation = "mcp"
    mcp_server = "yapo-mcp"
    mcp_tool = "route_prompt"

    [[tools]]
    name = "mem_write"
    description = "Store a fact into long‑term memory"
    parameters = [{ name = "text", type = "string", required = true }]
    concurrent_calls = 10
    timeout_seconds = 30
    implementation = "mcp"
    mcp_server = "yapo-mcp"
    mcp_tool = "mem_write"

    [[tools]]
    name = "mem_read"
    description = "Search long‑term memory"
    parameters = [{ name = "query", type = "string", required = true }]
    concurrent_calls = 10
    timeout_seconds = 30
    implementation = "mcp"
    mcp_server = "yapo-mcp"
    mcp_tool = "mem_read"

    [[tools]]
    name = "summarise_text"
    description = "Summarise text into bullet points"
    parameters = [
      { name = "text", type = "string", required = true },
      { name = "max_points", type = "integer", required = false }
    ]
    concurrent_calls = 10
    timeout_seconds = 30
    implementation = "mcp"
    mcp_server = "yapo-mcp"
    mcp_tool = "summarise_text"

    [[tools]]
    name = "web_search"
    description = "Search the web"
    parameters = [{ name = "query", type = "string", required = true }]
    concurrent_calls = 10
    timeout_seconds = 20
    implementation = "mcp"
    mcp_server = "searxng-mcp"
    mcp_tool = "web_search"

    [[tools]]
    name = "run_command"
    description = "Run a restricted shell command"
    parameters = [
      { name = "command", type = "string", required = true },
      { name = "timeout", type = "integer", required = false }
    ]
    concurrent_calls = 10
    timeout_seconds = 30
    implementation = "mcp"
    mcp_server = "shell-mcp"
    mcp_tool = "run_command"

8.3 Tool Registry Caching
    The runner uses `jobs/.tool_cache.json`. If the file does not exist,
    or if `config.toml` has a newer modification time than the cache file,
    the runner rebuilds the cache by calling `tools/list` on all MCP
    servers. Otherwise, the cached registry is used as‑is.

8.4 Tool Execution
    - For tool jobs, runner reads tool_call.json and sends it to the MCP
      server. Result is stored in output.txt.
    - During compaction (see §10) and routing, runner directly calls MCP
      tools inline.

9. RAG Pre‑fetch
------------------
To pre‑load context, create the main job in pending, then create tool
children with the appropriate --tool-json values. When children complete,
their output is appended to the main job’s context.txt, and once all
children are done, the main job moves to ready.

Example:
  main=$(jobber create --type main --state pending --model "" \
         --prompt-file task.txt)
  sub1=$(jobber create --type tool --state pending --parent $main \
         --tool-name mem_read \
         --tool-json '{"tool":"mem_read","arguments":{"query":"project 3791"}}')
  jobber move $sub1 ready

10. Context Compaction
----------------------
Trigger: when runner picks up a main job with no sub‑jobs and context.txt
size > compact_size_kb.

Procedure (performed by runner before any LLM call):
  1. Call summarise_text MCP tool with the content of context.txt.
  2. Call mem_write MCP tool with the summary, prefixed by the job_id.
  3. Call mem_read MCP tool with the job_id to retrieve related memories.
  4. Create a clone of the current job (same job_id, compact=true) via
     jobber. The clone’s context.txt is initialised with the retrieved
     memories.
  5. Move the original job to done, and the clone to ready.

The original job never calls the LLM; the clone will be scheduled later.

11. Lifecycle Example (Revised)
-------------------------------
a) User runs: init.py "search the web for iran usa war today" --mtype others
   jobber creates main job 1000 (type=main, model="gemma4:latest").
b) Scheduler runs 1000. Runner builds prompt with tools, calls LLM via
   conn_openai.
   LLM returns {"tool":"web_search","arguments":{"query":"iran usa war"}}.
   Runner creates tool child 1001, adds sub.1001, moves 1000→pending.
c) Scheduler runs 1001. Runner reads tool_call.json, calls the SearXNG
   wrapper, writes search results to 1001/output.txt. Runner propagates
   the result to 1000’s context.txt (prefixed with [TOOL:web_search]),
   removes sub.1001, moves 1000→ready.
d) Scheduler runs 1000 again. LLM now sees search results in context,
   returns {"done":true,"answer":"Here is a summary of the latest news…"}.
   Runner moves 1000→done.
e) (Loop‑guard scenario) If the LLM had requested web_search again despite
   the results, the loop guard would have forced a done after the second
   call, preventing an infinite loop.

12. GPU Energy Management
--------------------------
12.1 Configuration (config.toml)
    Servers have optional `mac_address` and `suspend_command` for power
    control. The GPU schedule supports an `on_demand` flag and idle timeout.

    [gpu_schedule]
    timezone = "Europe/London"
    on_demand = true
    idle_timeout_seconds = 60
    windows = [{ start = "22:00", end = "06:00" }]

12.2 Job Time Constraints
    Optional job.toml fields start_after / finish_by.

12.3 Scheduler Behaviour
    - Only dispatch GPU jobs if the server is schedulable and reachable.
      Reachability is checked via the backend connector, falling back to
      a TCP ping.
    - On‑demand mode (on_demand = true):
        * If a ready job needs the GPU and it is sleeping, send WoL to
          mac_address, wait 10 seconds, then proceed.
        * After all ready jobs are processed, if no new GPU jobs appear
          for idle_timeout_seconds, suspend the GPU via suspend_command.
        * If the GPU is already awake, it is used without power change.
    - Scheduled mode (on_demand = false):
        * GPU is powered on/off strictly according to the schedule windows.
        * If within a window and GPU sleeping → wake up.
        * At window end, wait for active jobs to finish, then suspend
          only if Yapo woke the GPU at window start (otherwise leave on).
    - Jobs with start_after are only considered after that time.
    - If a job’s finish_by has passed, move to error.

13. Capacity & Concurrency
----------------------------
- Scheduler tracks active jobs per server (only schedulable servers) and
  per tool type.
- Only processing jobs consume slots; pending jobs do not.
- GPU capacity is only considered when GPU is available (powered on and
  reachable).
- MCP tool concurrency is managed by `concurrent_calls` in the tool
  definitions; the scheduler enforces this for tool jobs.

14. Error Handling
-------------------
- Invalid LLM output → job moves to error (no retry).
- Infrastructure error (e.g., server unreachable) → job moves to error.
- Child failure: if parent has fail_on_child_error=true, parent moves to
  error; otherwise, child’s error is appended to parent’s context and the
  parent continues.
- Tool‑call loop guard: prevents infinite tool‑call loops by forcing a
  done after 2 identical tool calls and a hard cap of 5 total tool calls
  (see §5.2).

16. Backend Connection Modules
-------------------------------
- LLM calls use a pluggable backend system.  Modules are named
  `conn_<backend>.py` and must implement `generate()` and optionally
  `server_reachable()`.
- The default backend is `conn_openai.py`, which speaks the
  OpenAI‑compatible /v1/chat/completions protocol.
- Servers specify their backend via the `backend` field (defaults to
  `"openai"`).  An optional `api_key` field is supported for cloud
  providers.
- The scheduler checks reachability via the backend module; falls back
  to a TCP ping if the module does not provide `server_reachable()`.
