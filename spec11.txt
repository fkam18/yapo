Orchestrator Design v11 – spec11.txt (2026-07-09)
==================================================
This revision adds the Docker container deployment, the complete REST API
reference, the attachment system, the per‑model prompt templates with
ChatML support, the model_type semantics, the web dashboard with job
submission modal, and the GPU energy management with per‑server schedules.

1. Overview
-----------
Yapo (Yet Another Personal Orchestrator) is a home‑lab orchestrator that
manages stateless LLM jobs using a folder‑based job pool.  A jobber
serialises all state transitions.  The main loop (`yapo.py`) picks jobs
from the `ready` state, respects server and tool capacity, and forks
runner processes.  The runner assembles a standardised prompt, calls the
LLM via a pluggable backend connector, and parses a structured JSON
output.  Context accumulates across turns; when a main job’s context
becomes too large, the runner compacts it via MCP tool calls.

All tool execution (memory, summarisation, web search, shell commands,
and routing) is delegated to external MCP servers.  There are no separate
“embed”, “summarise”, or “router” job types – these are MCP tools called
directly.

LLM calls use `conn_openai.py`, which speaks the OpenAI‑compatible
/v1/chat/completions protocol (Ollama, llama.cpp, and cloud providers).

The system runs as a Docker container for 24×7 operation on a headless
server.  A REST API (served by the dashboard on port 3388) provides full
job lifecycle management, config reload, debug logging, and health checks.
An Ansible playbook handles one‑command deployment.

GPU energy management supports per‑server power schedules, Wake‑on‑LAN,
SSH‑based suspend, on‑demand mode with idle timeout, and per‑job time
constraints (start_after / max_job_duration).

All file operations are restricted to the configured `workspace` root.

2. Terminology
---------------
- **Job type** (`job.toml` field `"type"`): `"main"` or `"tool"`.
- **Model type** (`config.toml` model field `"type"`): classification
  used by the router or manual override.  Values: `"code"`, `"others"`,
  `"visual"`, `"embed"`, `"summarise"`, `"router"`, and user‑defined types.
- **Model name** (`config.toml` model field `"name"`): server‑side
  identifier passed to the LLM backend (e.g. `"others"`, `"coder"`).
  Multiple model types may share the same server‑side model name.

The CLI flag for forcing a model type is `--mtype`.  Available types are
read dynamically from `config.toml` by `init.py`.

3. Folder Structure & States
------------------------------
jobs/
  ready/         – jobs waiting to be picked by the scheduler
  processing/    – job currently being executed by a runner
  pending/       – job waiting for sub‑jobs (tool children) to finish
  done/          – job completed
  error/         – job failed (terminal)

All state changes are atomic via jobber (serialised by jobber.lock).

4. Job Folder Contents
-----------------------
  job.toml
    job_id            : 12‑char unique ID (same for entire task chain)
    type              : "main" or "tool"
    model_type        : model type string (e.g. "code", "others1").
                        Empty if not yet routed.
    parent            : parent job queue number (0 if none)
    name              : human‑readable job name (optional)
    tool_name         : for tool jobs (informational)
    start_after       : HH:MM string; job waits until that time today
                        (or next day if already past).  (optional)
    max_job_duration  : integer seconds; overrides global default.
                        Default: 900 (15 min).  (optional)
    fail_on_child_error : bool (default false)
    compact           : if true, created by compaction
  parent.<qno>      – empty file indicating parent queue number
  sub.<qno>         – empty file per direct child (managed by jobber)
  prompt.txt        – the task for this job
  context.txt       – accumulated context (tool results, memory, etc.)
  output.txt        – LLM response (JSON) or tool result
  full_prompt.txt   – (diagnostic) exact prompt sent to LLM
  tool_call.json    – present only in tool jobs; JSON to forward to MCP
  assets/           – optional attached files (text, images, etc.)

5. Component Summary
---------------------
5.1 jobber.py
    Serialised CRUD for jobs.  Key arguments:
      create  --type <type> --state <state>
              --model-type <model_type>   (default empty → router)
              [--parent <qno>] [--prompt-file <file>]
              [--tool-json '<json>'] [--job-name <name>]
              [--start-after HH:MM] [--max-job-duration <seconds>]
      move    <qno> <new_state>
      append  <qno> <file> <text>
      clone   <qno> --new-jobid <id>
      cleanup <qno>

    `--model-type` defaults to empty string.  When empty, the runner
    invokes the `route_prompt` MCP tool to classify the prompt.

    The `create_job()` function also accepts an `attachments` parameter
    (list of dicts with `filename`, `content` (base64), `mime`) for
    saving files to the job's `assets/` folder.

5.2 runner.py
    Executes a job from the processing state.
    - If type == "tool":
        Execute the MCP tool, write result, propagate to parent.
    - If type == "main":
        * If `model_type` is empty → call `route_prompt` MCP tool,
          store the returned classification in job.toml.
        * Look up model config by `type` to get server model name,
          server URL, options, and prompt_template.
        * Build prompt using the model's `prompt_template` if present,
          otherwise use the default XML template.
        * `route_prompt` is excluded from the tool list sent to the LLM.
        * Inject dynamic convergence note via `{{convergence_note}}`.
        * Detect `assets/` folder: text files wrapped in `<FILE>` blocks;
          images base64‑encoded and passed to vision models.
        * Call LLM, parse JSON output, handle tool calls / done.
    **Tool‑call loop guard:** hard cap of 5 total tool calls.
    **Dynamic convergence:** three‑tier escalation injected at build time.

5.3 yapo.py (scheduler)
    Forever loop:
      - Enforces start_after, max_job_duration, server/tool capacity.
      - Per‑server GPU schedule (windows, on‑demand, WoL, SSH suspend).
      - Handles SIGHUP to reload config at runtime.

5.4 init.py (CLI, dev‑only)
    Creates a main job from a user prompt.
    Usage: init.py "prompt"
           [--mtype <model_type>]
           [--name "job name"]
           [--start-after HH:MM]
           [--max-duration <seconds>]
           [--rag <tool>:<query> ...]

5.5 dashboard.py (Web UI + REST API)
    Serves the web dashboard on port 3388 and the full REST API.
    See §17 for complete API reference.

5.6 conn_openai.py
    Pluggable backend connector for OpenAI‑compatible APIs.
    Supports multimodal messages for vision models.
    Debug logging to `/tmp/openai.txt` controlled by environment
    variable `CONN_OPENAI_DEBUG` (default: false).  Can be toggled
    at runtime via `PATCH /api/config`.

5.7 Auxiliary tools
    - `catjob.py <qno>` – prints job details and output.
    - `catanswer.py` – extracts the `answer` field as plain text.
    - `convert-config.py` – converts laptop config.toml to Docker‑ready
      config.toml.j2 with Ansible variables.

6. Prompt Templates
--------------------
6.1 Default XML Template
    Used when a model has no `prompt_template` in config.toml.
    Structure: <GOAL>, <CONTEXT>, <TOOLS>, <RULES>, <TASK>.

6.2 Per‑Model Templates
    Models may specify a `prompt_template` string in config.toml.
    The runner substitutes:
      {{goal}}            – original user prompt
      {{context}}         – content of context.txt (or "(none)")
      {{tool_list}}       – generated tool list (route_prompt excluded)
      {{task}}            – current job prompt
      {{convergence_note}} – dynamic escalation text

    Example (ChatML with reasoning limit):
    <|im_start|>system
    You are an expert assistant. Think briefly (max 3 sentences), then
    provide your answer.  Output ONLY valid JSON.
    {{convergence_note}}
    <|im_end|>
    <|im_start|>user
    Goal: {{goal}} ...

7. LLM Output Parsing
----------------------
Valid outputs:
  - {"tool": "...", "arguments": {...}}
  - {"done": true, "answer": "..."}
Markdown fences are stripped before parsing.  `extract_json()` handles
malformed responses by extracting the first valid JSON object.

8. Tool System & MCP Integration
---------------------------------
All tools are backed by MCP servers.  `route_prompt` is an internal tool
never shown to the LLM; called only by the runner when model_type is empty.

9. RAG Pre‑fetch
------------------
To pre‑load context, create the main job in pending, then create tool
children with the appropriate --tool-json values.  When children complete,
their output is appended to the main job’s context.txt, and once all
children are done, the main job moves to ready.

10. Context Compaction
----------------------
Trigger: when runner picks up a main job with no sub‑jobs and context.txt
size > compact_size_kb.

Procedure:
  1. Call summarise_text MCP tool with the content of context.txt.
  2. Call mem_write with the summary, prefixed by the job_id.
  3. Call mem_read with the job_id to retrieve related memories.
  4. Create a clone of the current job; clone’s context.txt is
     initialised with the retrieved memories.
  5. Move the original job to done, and the clone to ready.

11. Lifecycle Example
----------------------
a) init.py "write a Rust program for a 9x9 Go game" (no --mtype).
   jobber creates main job 1000 (model_type="").
b) Scheduler runs 1000.  Runner calls route_prompt → "code".
c) Runner looks up model type "code" → server model "coder",
   ChatML template with "output code directly" instruction.
d) LLM returns {"done":true,"answer":"fn main() { ... }"}.
   Runner moves 1000→done.

12. GPU Energy Management
--------------------------
Per‑server schedule inside the server block in config.toml.
    [servers.gpu_schedule]
    timezone = "Europe/London"
    on_demand = true
    idle_timeout_seconds = 60
    windows = [{ start = "22:00", end = "06:00" }]

Jobs can specify start_after (HH:MM) and max_job_duration (seconds).
The scheduler enforces both.  WoL and SSH suspend use the server's
mac_address and suspend_command fields.

13. Capacity & Concurrency
----------------------------
- Scheduler tracks active jobs per server (only schedulable servers) and
  per tool type.
- Only processing jobs consume slots; pending jobs do not.
- GPU capacity only considered when GPU is available (powered on and
  reachable).

14. Error Handling
-------------------
- Invalid LLM output → job moves to error (no retry).
- Infrastructure error → job moves to error.
- Tool‑call loop guard: hard cap of 5 total tool calls.
- max_job_duration violations move the job to error.

16. Docker Deployment
-----------------------
The project includes a `docker/` directory with everything needed to
build, deploy, and manage the containerised Yapo service.

Files:
  Dockerfile           – Python 3.11‑slim image with chromadb, sqlite3,
                         openssh-client, procps.
  docker-compose.yml   – Service definition with named volume, config
                         mount, secrets mount, host network mode.
  build.sh             – Builds the Docker image and exports yapo.tar.gz.
  deploy-to-app1.sh    – One‑command Ansible deploy.
  deploy.yml           – Ansible playbook (copies image, writes config,
                         loads image, starts container).
  inventory.ini        – Ansible inventory (app1.alt).
  config.toml.j2       – Jinja2 template for config.toml with Docker paths
                         and Ansible variables.
  convert-config.py    – Generates config.toml.j2 from the working
                         config.toml (run by build.sh).
  entrypoint.sh        – Starts yapo.py (background) + dashboard.py
                         (foreground) inside the container.
  requirements.txt     – Python dependencies (chromadb, tomli).

The container runs with `network_mode: host` for WoL broadcast support.
Port 3388 is exposed for the dashboard/API.

17. REST API Reference
------------------------
All endpoints are served by `dashboard.py` on port 3388.

17.1 Job Submission & Retrieval
    POST   /api/submit
        Body: {"prompt":"...", "mtype":"code", "name":"...",
               "start_after":"22:00", "max_duration":"900",
               "rags":["mem_read:query"], "attachments":[...]}
        Returns: {"success":true, "qno":"42"}

    GET    /api/job/<qno>
        Returns: {"state":"done", "output":"...", "model_type":"...", ...}

    GET    /api/job/<qno>?wait=true&timeout=300
        Blocks until job reaches "done" or "error" (or timeout).
        Returns job details.  If timeout reached, includes "timed_out":true.

    GET    /api/job/<qno>/download
        Downloads the full job folder as a .tar.gz file.

17.2 Job Listing
    GET    /api/tree
        Returns the full job hierarchy as nested JSON:
        {"1": {"state":"done","job_type":"main","children":[4,5,6]}, ...}

17.3 Job Deletion
    DELETE /api/job/<qno>
        Recursively deletes the job and all its descendants.

    DELETE /api/jobs?from=10&to=50&state=done
        Bulk‑deletes jobs in a range, optionally filtered by state.

17.4 Config & Reload
    GET    /api/config
        Returns the current config.toml as JSON.

    POST   /api/reload
        Sends SIGHUP to yapo.py to reload config at runtime.

    PATCH  /api/config
        Body: {"key":"CONN_OPENAI_DEBUG","value":"true"}
        Updates runtime configuration keys.

17.5 Debug & Monitoring
    GET    /api/logs?lines=100
        Returns the last N lines of the scheduler log.

    GET    /api/debug/openai
        Downloads the OpenAI API debug log (/tmp/openai.txt).

    GET    /api/health
        Returns {"status":"ok"} if the service is running.

17.6 Dashboard UI
    GET    /
        Serves the interactive web dashboard.

    GET    /api/queues
        Returns the HTML fragment for the job queue panel (used by the
        dashboard's auto‑refresh).

18. Attachment System
-----------------------
Jobs can include file attachments (text, code, images, PDFs).
Attachments are uploaded via the dashboard UI or the REST API as base64
in the "attachments" array of /api/submit.  They are saved to the job's
assets/ folder.

At runtime, the runner:
  - Text files → injected into context as <FILE path="...">content</FILE>
  - Images → base64‑encoded and passed to vision models via the OpenAI
    multimodal message format.

----------------

ADDENDUM – spec11.txt (2026-07-09)
====================================

A. Central Logging Module (log.py)
------------------------------------
A new module `log.py` provides thread‑safe, non‑blocking log write and
destructive log read operations.

  log_write(line)
      Appends a line to /tmp/yapo.log under a file lock (fcntl.flock).
      If the lock cannot be acquired within 1 second, the line is silently
      dropped.  If the file exceeds 1 MB (MAX_SIZE), it is automatically
      truncated to zero before the write.

  log_read(max_lines=100)
      Reads and returns the last `max_lines` lines from /tmp/yapo.log,
      then truncates the file to zero (destructive read).  No locking is
      used on read.

All previous FIFO‑based logging (log.pipe) has been removed.  The log
file replaces the pipe, eliminating blocking writes and the need for
background drain processes.

B. Log Line Format
--------------------
Every log line is prefixed with a source tag and timestamp:

  yapo 2026-07-09 22:00:01: <message>
  openai 2026-07-09 22:00:15: === API Call === ...

yapo.py writes via a custom stderr wrapper (`LogStderr`) that calls
log_write() with the "yapo" prefix.  conn_openai.py calls log_write()
directly with the "openai" prefix when CONN_OPENAI_DEBUG is true.

C. Dashboard Changes
----------------------
- `/api/logs` now calls log_read() instead of reading a FIFO.  Returns
  immediately with available lines (non‑blocking).
- `/api/debug/openai` removed.  Consumers filter openai lines with
  `grep openai` on the /api/logs output.
- `/api/stream` (SSE) remains on a named pipe (event.pipe) for UI refresh
  signalling.  This pipe carries only 1‑byte events and does not block
  writers (O_NONBLOCK).  The SSE handler runs in its own thread via
  ThreadingHTTPServer.

D. entrypoint.sh (Simplified)
-------------------------------
No log pipe, no drain process.  Only the SSE event pipe is created.

  #!/bin/bash
  mkdir -p /home/yapo/yapo_root/jobs/{ready,processing,pending,done,error}
  mkfifo /home/yapo/yapo_root/event.pipe 2>/dev/null || true
  python3 yapo.py &
  python3 dashboard.py

E. conn_openai.py
-------------------
DEBUG_DUMP now writes to log_write() instead of a separate file or pipe.
The environment variable CONN_OPENAI_DEBUG controls whether API calls
are logged.

F. yapo.py
------------
The custom `LogStderr` class replaces the previous `PrefixedStderr`.
All stderr output is routed through log_write() with the "yapo" prefix
and timestamp.
